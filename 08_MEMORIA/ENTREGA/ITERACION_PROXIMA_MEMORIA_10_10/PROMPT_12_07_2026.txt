## 4.2. Texto base

Utiliza como base el siguiente contenido, pero intégralo y mejóralo para que encaje académicamente en el Capítulo IV:

### 4.3.3. Control de versiones y trazabilidad del desarrollo

Durante el desarrollo del proyecto se aplicó un sistema de versionado progresivo para controlar la evolución de scripts, artifacts, runners, configuraciones y documentos de apoyo. El objetivo fue conservar la trazabilidad de los cambios, evitar la pérdida de versiones funcionales y diferenciar claramente entre archivos en desarrollo, versiones candidatas y componentes validados.

Las distintas iteraciones se identificaron mediante nombres de archivo con número de versión o estado, empleando términos como `v1`, `v2`, `candidate`, `validated`, `final` o `patched`. Cada nueva versión se generó a partir de la anterior cuando era necesario corregir errores, ampliar funcionalidades o adaptar el comportamiento a los resultados obtenidos durante las pruebas. Este procedimiento fue especialmente relevante en los runners globales, los scripts de las técnicas TEC-001 a TEC-009 y los artifacts personalizados de Velociraptor.

El ciclo de trabajo seguido fue el siguiente:

1. Desarrollo inicial del script o artifact.
2. Ejecución en el laboratorio controlado.
3. Revisión de logs, resultados y evidencias.
4. Corrección de errores o ajuste de la lógica.
5. Creación de una nueva versión sin sobrescribir la anterior.
6. Validación mediante una nueva ejecución.
7. Traslado de la versión estable a los directorios de archivos validados o finales.

Además del versionado mediante nombres de archivo, se utilizó Git como sistema de control de versiones. El proyecto se almacenó en un repositorio Git local y se sincronizó con GitHub, lo que permitió conservar un historial de cambios mediante commits, comparar versiones mediante diferencias de contenido y disponer de una copia remota del trabajo.

La estructura del repositorio se organizó separando contexto, artifacts, scripts, runners, evidencias, documentación y memoria. Antes de registrar cambios se revisaba el estado del repositorio mediante `git status` y, posteriormente, se añadían los archivos modificados, se generaba un commit descriptivo y se sincronizaba con el repositorio remoto.

Los comandos básicos empleados fueron:

```powershell
git status
git add .
git commit -m "Descripción de los cambios realizados"
git push origin main
```

Para reducir el riesgo de incorporar archivos innecesarios o sensibles, se excluyeron mediante `.gitignore` elementos como archivos temporales de Word, copias de seguridad, logs excesivamente pesados, credenciales y configuraciones que pudieran contener información sensible.

El uso combinado de versionado manual, hashes SHA-256, Git y GitHub permitió mantener una trazabilidad completa del desarrollo. De esta forma, fue posible identificar qué versión de cada script, artifact o runner se utilizó en las campañas finales y relacionarla con las evidencias y resultados incluidos en la memoria.
