1. CONTEXTO GENERAL DEL TFM
============================================================

Estoy desarrollando un TFM sobre la evaluación de Velociraptor como herramienta HIDS/DFIR para detectar técnicas MITRE ATT&CK en Windows.

Enfoque aproximado:
“Evaluación de Velociraptor como HIDS/DFIR para la detección de técnicas MITRE ATT&CK asociadas a ransomware, sabotaje, exfiltración e insiders en entornos Windows”.

Objetivo principal:
Verificar si Velociraptor puede funcionar como herramienta HIDS/DFIR mediante artifacts.

Aspectos a evaluar:
1. Capacidad de detección host-based.
2. Necesidad de adaptar artifacts al entorno concreto.
3. Comparación entre artifacts estándar, comunitarios y personalizados.
4. Calidad de alerta.
5. Reducción de falsos positivos.
6. Impacto en rendimiento.
7. Utilidad real frente a enfoques EDR/SIEM/HIDS tradicional.
8. Diferencia entre visibilidad, detección, alerta RT y salida externa.
9. Trazabilidad entre caso de uso, técnica MITRE, telemetría y evidencia.
10. Viabilidad de Velociraptor como plataforma HIDS/DFIR, no como sustituto directo de un EDR comercial.

Decisión sobre FortiEDR:
- No realizar comparación experimental con FortiEDR.
- Usar EDR/SIEM/HIDS solo como marco conceptual.
- No prometer métricas ni resultados empíricos de FortiEDR si no se han probado.
- No plantear conclusiones del tipo “Velociraptor es mejor/peor que FortiEDR”.
- Formular la comparación como diferencia conceptual:
  - Velociraptor: plataforma DFIR/HIDS flexible basada en artifacts.
  - EDR: producto orientado a detección, respuesta, correlación y gestión operacional integrada.
  - SIEM: agregación, correlación y explotación centralizada de eventos.
  - HIDS clásico: monitorización host-based con reglas/firmas/configuración local.

Frase lista para memoria:
“El estudio no plantea una comparación experimental directa con FortiEDR, al no disponer de un entorno equivalente de evaluación. La comparación se limita al plano conceptual, utilizando EDR, SIEM e HIDS tradicional como referencias funcionales para contextualizar el alcance de Velociraptor como plataforma host-based de monitorización, detección y análisis forense.”

No se transfiere el archivo ZIP ni información real fuera del equipo; por tanto, la técnica se interpreta principalmente como T1074.001 y T1560.001, mientras que T1020/T1041 solo se consideran de forma contextual si la telemetría de red queda documentada.”

6. PRIORIZACIÓN ENTRE TÉCNICAS
============================================================

Cuando una misma evidencia contiene varias señales, usar este orden:

1. TEC-007: crypto/ransomware.
2. TEC-009: staging/compresión/copia/conexión externa.
3. TEC-008: destrucción/borrado.
4. TEC-006: discovery.
5. TEC-001: PowerShell sospechoso genérico.

Ejemplos:
- Si un ScriptBlock contiene Remove-Item + Compress-Archive + Copy-Item, clasificar como TEC-009, no como TEC-008.
- Si contiene AES/CryptoStream/.aes, clasificar como TEC-007 aunque también haya eliminación de .aes.
- Si aparece Get-CimInstance SecurityCenter2 dentro de un flujo más amplio de staging o ransomware, Discovery queda como señal secundaria, no como alerta principal.
- Si solo aparece Set-ExecutionPolicy Bypass, clasificar como PowerShell sospechoso genérico, no como ransomware.

Regla general:
- La clasificación debe basarse en el comportamiento de mayor impacto y mayor especificidad.
- Priorizar señales de mayor valor semántico sobre indicadores genéricos.
- Evitar duplicar alertas por la misma ejecución si pueden consolidarse en una alerta de mayor prioridad.

8. ANTI-FALSOS POSITIVOS
============================================================

Ruido detectado:
- MSFT_ScheduledTask.
- __cmdletization.
- Export-ModuleMember.
- Microsoft.PowerShell.Cmdletization.
- cim:DeleteInstance.
- .EXTERNALHELP.
- TrustedInstaller.exe.
- TiWorker.exe.
- Velociraptor loopback 8443.
- Sysmon Configuration Update.
- Net Conn genérico.
- File Deleted genérico.
- Chrome/svchost de red no relacionado.
- PowerShell administrativo legítimo.
- Instaladores que modifican Run Keys.
- Servicios legítimos creados por actualizaciones o software corporativo.

Regex recomendado para ruido PowerShell:
(?i)(__cmdletization|Export-ModuleMember|MSFT_ScheduledTask|Microsoft\.PowerShell\.Cmdletization|cim:DeleteInstance|\.EXTERNALHELP)

No excluir por sí solos:
- ForEach-Object.
- Where-Object.
- Select-Object.

Motivo:
- Scripts reales los usan.
- Excluirlos globalmente puede ocultar TEC-008/TEC-009.

Criterio anti-FP:
- No eliminar señales útiles globalmente si pueden aparecer en comportamiento malicioso.
- Usar scoring o combinación de condiciones.
- Priorizar detecciones por conjunción:
  - proceso + comando + evento + contexto.
- No alertar por eventos aislados de bajo valor salvo que el CU lo justifique.

Ejemplos:
- ForEach-Object solo: no alertar.
- Remove-Item + -Recurse + -Force + múltiples ficheros: alertar.
- PowerShell solo: visibilidad.
- PowerShell + EncodedCommand + IEX/DownloadString: detección.
- Sysmon ID 26 individual: evidencia.
- Muchos ID 26 asociados a un mismo proceso/script: alerta consolidada.

11. DISCORD / SERVER_EVENT

El SERVER_EVENT debe:

- Normalizar la salida.
- No detectar por sí mismo.
- Actuar como router/capa de salida externa.

Fuentes que NO deben enviar Discord directamente:
- Sysmon ID 26 por fichero.
- Raw 4104 completo.
- Ransomware threshold periódico sin consolidación.
- Debug/raw sources.
- Fuentes masivas de evidencia.
- TrackNetworkConnections sin filtro.

19.6. Escritura JSONL con PowerShell y problema de los dos puntos
------------------------------------------------------------

Error observado:
- PowerShell devolvió ParserError:
  Token ':' inesperado en "RouterTime"

Causa:
- El JSON serializado se estaba pasando en bruto a PowerShell.
- PowerShell interpretó fragmentos del JSON como código, especialmente claves con dos puntos:
  "RouterTime": ...

Solución validada:
1. Serializar el evento como JSON en VQL.
2. Convertir el JSON a Base64.
3. Pasar Base64 a PowerShell.
4. Decodificar Base64 en PowerShell.
5. Escribir el JSON resultante con Add-Content.

Patrón recomendado:
- VQL:
  base64encode(string=serialize(format="json", item=dict(...)))

- PowerShell:
  $json=[System.Text.Encoding]::UTF8.GetString([System.Convert]::FromBase64String($b64))
  Add-Content -LiteralPath $p -Value $json -Encoding UTF8

Regla para Codex:
- No pasar JSON bruto como argumento de PowerShell.
- Usar Base64 para transportar JSON desde VQL a PowerShell.
- Revisar siempre ReturnCode, Stdout y Stderr en la salida del SERVER_EVENT.

============================================================

Frase sobre P3_v4:
"Durante la iteración P3_v4, el perfil comportamental medio dejó de apoyarse exclusivamente en PowerShell Script Block Logging e incorporó fuentes mínimas de Sysmon EventID 1 para cubrir comportamientos que, en la campaña real, no quedaban representados de forma suficiente en 4104. Esta decisión se mantiene dentro del perfil P3 al no activar correlación forense intensiva ni eventos de alto volumen como Sysmon ID 26 como alerta individual."

Frase sobre CU-009:
"TEC-009 se interpreta como una simulación de staging y archivado local complementada con telemetría de red contextual. La ejecución generó archivos ZIP en el endpoint y eventos Sysmon de resolución DNS y conexión TCP externa desde powershell.exe, pero no evidenció transferencia efectiva del ZIP ni de datos reales. Por tanto, la técnica se documenta como T1074.001/T1560.001 con contexto de red, sin afirmar exfiltración real."

Frase sobre router:
"La validación del router SERVER_EVENT confirmó que la capa de enrutado no constituye detección, sino persistencia de alertas ya emitidas por CLIENT_EVENT. Para evitar errores de escritura JSONL, el evento normalizado se serializa y transporta en Base64 hacia PowerShell, usando parámetros explícitos y registrando ReturnCode, Stdout y Stderr como campos diagnósticos."

Frase sobre límites:
"Los resultados de esta fase no deben interpretarse como resultados finales de detección, sino como una iteración de depuración de telemetría, clasificación semántica y enrutado. La aceptación final de cada artifact requiere una nueva campaña controlada, revisión de falsos positivos, comprobación de cobertura por CU y análisis posterior de rendimiento."
